## What PR #62 actually changes

1. `NodeConfig.extra_vllm_args` + `NodeConfig.engine_image` — per-instance, threaded through
   `_OVERRIDE_KEYS` so they persist and survive restart-replay. A caller-supplied flag
   **suppresses** the matching built-in (vLLM errors on duplicates).
2. The 0.17-era GB10 workarounds (`--enforce-eager`, NVFP4 MARLIN env) now apply **only** to
   the pinned default image. They are bugs in that build; on 0.27.1 they only cost throughput.
3. `vllm serve` argv normalized across engine images — `vllm/vllm-openai` bakes
   `ENTRYPOINT ["vllm","serve"]`, the default image uses NVIDIA's passthrough shim. Entrypoint
   is deliberately NOT overridden (that would bypass CUDA setup).
4. Catalog entries carrying proven recipes for both models, applied as defaults so a bare
   `{"model": "..."}` load (what the dashboard sends) launches correctly.
5. Robustness: dropped `docker run --rm` (crashed engines used to erase themselves, leaving
   no logs); `start_solo()` now confirms the container reached Running and logs the engine's
   last output on failure; eject persists across reboot; boot path no longer launches the
   legacy host-venv engine when vLLM isn't importable.

### ⚠️ Two deployment traps (read before rebooting any node)

- **spark-3 and spark-4 run a hand-built dev image started with `docker run`, and their
  systemd unit is STOPPED.** Container restart policy is `no`. A host reboot brings back
  whatever systemd says, and the recipe support disappears — Nemotron and Qwen3.8 would fail
  to reload with their flags.
- **Every node's systemd unit still points at `ghcr.io/getainode/ainode:0.5.0`**, even the
  nodes running 0.5.3. So `ainode update` swaps the running container without rewriting the
  unit. This is PRE-EXISTING (not from this session's work), but it means a reboot is
  effectively a downgrade on any node.

## Next step (the recommended path)

1. **Merge PR #62.**
2. Let CI build + publish the image (self-hosted aarch64 runner → GHCR).
3. `ainode update` across all four nodes so everything lands on the same released version
   through the normal pipeline. **Do NOT hand-copy dev images to spark-1/spark-2** — that is
   how the fleet ended up on four different versions.
4. Optionally, in the same pass: fix the stale systemd units so "installed" and "running"
   finally agree and reboots stop being downgrades.

## Proven model facts (don't re-derive)

- **Nemotron 3.5 Lightning 30B-A3B NVFP4** (MoE, 3B active): **104 t/s** single-stream,
  **504 t/s** at 16 streams, 1M ctx, text only. Rubric 19/19. Needs vLLM 0.27.1.
- **Qwen3.8-27B NVFP4** (dense, native vision): **19 t/s** with MTP spec decode (11.8 without),
  147 t/s at 16 streams, 262K ctx. Rubric effectively 23/23 after config fixes.
  **`--tool-call-parser qwen3_coder` is REQUIRED** (hermes silently parses zero tool calls).
  **Use temperature 0 for OCR**; at 0.7 it misreads characters.
- Dense models are bandwidth-bound on GB10 — that is why the dense 27B is ~9x slower per
  token than the MoE. This is physics, not misconfiguration.
- fp8 KV corrupts vision models on GB10. The auto-downgrade only fires for models on local
  disk, so an HF-cache-served VLM needs `--kv-cache-dtype auto` stated explicitly.
